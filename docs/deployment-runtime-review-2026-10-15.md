# 배포 런타임 검토 (2026-10-15)

## 재현 결과

- 운영 사용자 화면: `https://ppodeuk-user.vercel.app/`
- 운영 API: `https://ppodeuk-backend.up.railway.app`
- 첫 화면은 렌더링됐지만 추천 API가 5초 제한을 넘으면 예시 카드로 대체됐다.
- 예약 화면은 같은 상황에서 `AxiosError: timeout of 5000ms exceeded` 후 일반 오류 화면으로 전환됐다.
- API를 직접 호출했을 때 첫 응답은 3.65초, 이어진 두 응답은 각각 0.34초와 0.35초였다. 백엔드 기동 뒤에는 정상 응답했다.
- 비로그인 사용자가 예약 내역에 접근하면 로그인 화면으로 이동하고 원래 목적을 안내했다.
- 사업자 화면은 데모 데이터로 정상 렌더링됐으며 브라우저 콘솔 오류는 없었다.
- 390×844 모바일 화면에서 홈, 예약 목록, 세차장 상세, 비로그인 로그인 유도까지 클릭 흐름을 확인했다.
- 검색 API가 반환한 세차장 이미지 34개는 모두 HTTP 200과 `image/jpeg`로 응답했다.

## 적용한 완화

- API 요청 제한을 5초에서 30초로 늘렸다.
- 네트워크 오류, 408, 429, 5xx 조회 요청은 1.5초 뒤 한 번만 재시도한다.
- 추천 조회 대기 중 예시 카드를 실제 데이터처럼 즉시 노출하지 않는다.
- 대기 중에는 Railway 콜드 스타트와 1회 재시도를 포함해 최대 1분 정도 걸릴 수 있음을 안내하고, 최종 실패 뒤에만 예시 카드임을 명시한다.
- 외부 세차장 이미지가 로드되지 않으면 로컬 대체 이미지로 한 번만 교체한다.
- 홈과 하단 내비게이션의 최대 너비를 맞춰 데스크톱에서도 모바일 UI가 과도하게 늘어나지 않게 했다.
- 최종 조회 오류 화면에는 현재 페이지를 다시 불러오는 `다시 시도` 동작을 제공한다.

## 운영 권고

1. 현재는 Railway Free와 Serverless를 유지한다. 무료 또는 매우 낮은 트래픽을 위해 다른 무료 서비스로 이동해도 대부분 scale-to-zero와 콜드 스타트가 다시 생긴다.
2. 포트폴리오 제출이 집중되는 기간에는 Hobby 전환 또는 상시 실행을 검토한다.
3. 전환 전 일주일간 Railway Usage 화면에서 API와 DB의 실제 메모리·CPU 사용량을 측정해 Free 또는 Hobby 제공 범위 안에 드는지 확인한다. 유료 전환 시 Compute hard limit과 알림을 함께 설정한다.
4. 모니터링은 `/actuator/health` 같은 가벼운 헬스 엔드포인트, API 오류율, p95 응답 시간, DB 재시작 여부를 기준으로 한다. 비용 회피 목적으로 외부 ping을 보내 sleep을 우회하지 않는다.
5. DB의 `Server shutdown in progress`가 다시 발생하면 앱 콜드 스타트와 별개로 Railway 이벤트 및 DB 로그를 확인하고, 연결 풀의 validation과 재연결 설정을 점검한다.

## 대안 판단

- Render Free는 유휴 15분 뒤 내려가고 재기동이 약 1분 걸릴 수 있어 현재 문제를 악화시킬 수 있다.
- Koyeb Free도 유휴 1시간 뒤 scale-to-zero가 강제된다. 일반 유료 인스턴스는 대안이지만 마이그레이션 이득이 작다.
- Google Cloud Run은 0 인스턴스로 두면 비용은 낮지만 콜드 스타트가 남고, 최소 인스턴스 1은 비용이 발생한다. 현재 MySQL까지 함께 옮기면 운영 복잡도가 커진다.
- 따라서 단기적으로는 Railway 유지와 프런트 완화가 가장 낮은 위험의 선택이다. 무중단 첫 응답이 제품 요구사항이 되면 Railway 상시 실행 또는 고정비 VM/PaaS 유료 인스턴스로 전환한다.
